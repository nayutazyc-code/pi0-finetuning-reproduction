# 在 Mac 上搭建“香蕉放入开口盒子”场景

## 1. 先运行本地预览

在 **Mac 的终端**执行：

```bash
cd '/path/to/pi0-repro'
bash scripts/run_mac.sh scene --config configs/banana_box.toml
```

这是新加的本地场景入口。它复用当前环境中的 ALOHA 双臂、桌子、相机和位置控制器，加入可移动香蕉与固定开口盒子。无需新增依赖，也无需为场景预览连接云服务器。

窗口操作：

| 操作 | 效果 |
|---|---|
| `1` | 切换到俯视相机 `top` |
| `2` | 切换到斜视相机 `angle` |
| 空格 | 暂停或继续物理步进 |
| `R` | 按启动时的配置重置物体和机械臂 |
| `S` | 保存当前相机的 PNG 图片 |
| 关闭窗口 / 终端 `Ctrl+C` | 结束预览 |

也可以直接选择斜视：

```bash
bash scripts/run_mac.sh scene --config configs/banana_box.toml --camera angle
```

只想先得到一张场景图：

```bash
bash scripts/run_mac.sh scene --config configs/banana_box.toml --snapshot-only
```

程序在 `outputs/scene-日期-时间-编号/` 保存：

- `scene.png`：重置并经过初始沉降后的画面。
- `scene.json`：本次实际使用的位置、质量、摩擦等配置。
- `scene.xml`：组装完成的 MuJoCo 模型；内部 mesh 使用这台 Mac 的绝对路径，移到其他机器时应使用源码重新组装。
- `view-*.png`：按 `S` 后额外保存的画面。

**本项目已在独立 position_pd 配置中实际运行脚本专家并采到候选演示；此处基础场景的搭建参数与该配置的区别见 [仿真专家演示采集](仿真专家演示采集.md)。**

## 2. 这几个文件分别管什么

| 文件 | 负责什么 |
|---|---|
| `configs/banana_box.toml` | 香蕉与盒子放在哪里、香蕉转多少度、质量和摩擦、相机 |
| `src/pi0_repro/assets/banana_box.xml` | 香蕉的形状、盒子的尺寸、颜色、碰撞结构 |
| `src/pi0_repro/scene.py` | 读取原 ALOHA 模型，移除方块，加入新物体并预览 |

程序在内存中组合模型，读取已安装的 `gym-aloha==0.1.1` 机器人资源。自定义物体的源码保存在本项目中，便于以后复制到云端或纳入 Git 管理。

```text
ALOHA 机械臂、桌子、相机、控制器
                   +
       香蕉与开口盒子的物体 XML
                   +
          TOML 中的摆放和物理参数
                   ↓
        MuJoCo 模型 → 物理步进 → 相机画面
```

## 3. 第一步：改物体的摆放

编辑 `configs/banana_box.toml`：

```toml
[scene]
banana_position = [0.18, 0.48, 0.045]
banana_yaw_degrees = 10.0
banana_mass_kg = 0.12
banana_friction = [0.8, 0.005, 0.0001]
box_position = [0.13, 0.72, 0.0]
camera = "top"
settle_seconds = 0.6
```

位置的三个数依次是世界坐标中的 x、y、z，单位为米：

- x：沿桌子的横向。
- y：沿桌子的纵向。
- z：竖直向上；当前 ALOHA 桌面上表面位于 z=0。
- 香蕉位置是刚体参考点的位置；初始 z=0.045 让它从桌面上方落下，随后与桌面接触。
- 盒子位置是底面中心的位置；当前盒子固定，z=0 表示底面贴着桌面。
- `banana_yaw_degrees` 表示绕竖直轴旋转多少度，90 度就是在桌面上转四分之一圈。

例如，把香蕉沿 x 方向移动 5 厘米：将第一个数从 `0.18` 改为 `0.23`。

**保存配置后，关闭并重新运行预览。** 窗口中的 `R` 使用本次启动时读入的配置，不会重新读取磁盘文件。

当前桌面的范围约为 x 在 -0.61 到 0.61 米、y 在 0.219 到 0.981 米之间。物体也有体积，摆放时要给边缘留空间，并避开机械臂。机械臂是否能顺畅到达抓取点与盒子内部，需要后续用控制器检查，不能只靠画面判断。

## 4. 第二步：理解香蕉是怎么造出来的

目前的香蕉是 **由四个黄色胶囊体组合成的弯曲刚体**。它是便于入门的近似模型，质量、惯量和摩擦参数也是初始假设；不包含果肉形变或真实材质标定。

XML 中的一个组成部分：

```xml
<geom name="banana_segment_0"
      type="capsule"
      size="0.014"
      fromto="-0.055 0.004 0 -0.025 -0.009 0"
      rgba="0.96 0.78 0.05 1"/>
```

逐项理解：

- `geom`：一块可显示、可参与碰撞的几何体。
- `capsule`：两端圆滑的胶囊形状。
- `size="0.014"`：这里表示胶囊半径为 1.4 厘米。
- `fromto`：这段胶囊中轴线的起点和终点，都在香蕉自身的局部坐标系里。
- `rgba`：红、绿、蓝、透明度，取值通常在 0 到 1 之间。

四段胶囊属于同一个 `body`，彼此的相对位置固定，共同组成一根香蕉。这个 `body` 有 `freejoint`，因此香蕉能整体平移、旋转和被夹起。棕色两端只用于显示，碰撞由黄色部分定义。

以后要换成逼真的香蕉，可以增加 mesh 视觉模型，并保留若干简单几何体作为碰撞模型。弯曲物体若只用单个凸包碰撞，可能会把弯曲内侧的空隙也包进去，抓取接触形状就会失真。具体模型属性见 [MuJoCo 2.3.7 的 geom 文档](https://mujoco.readthedocs.io/en/2.3.7/XMLreference.html#body-geom)。

## 5. 第三步：理解开口盒子

盒子由 **一块底板和四面墙** 组成，五块几何体都参与碰撞，顶部留空。

当前外部尺寸约为：长 26 厘米、宽 20 厘米、高 10 厘米；内部开口约为 24 厘米乘 18 厘米，底板厚 1 厘米。

底板这一行：

```xml
<geom name="box_bottom" type="box"
      pos="0 0 0.005" size="0.13 0.10 0.005"/>
```

MuJoCo 中，`type="box"` 的 `size` 是三个方向的 **半尺寸**。因此这块底板的完整尺寸为 0.26 米 × 0.20 米 × 0.01 米。其中心在局部 z=0.005，所以下表面为 z=0、上表面为 z=0.01。[官方定义](https://mujoco.readthedocs.io/en/2.3.7/XMLreference.html#body-geom)

想加宽盒子时，需要一起调整底板、前后墙的长度，以及左右墙的位置，才能保持四壁闭合。初学时先只改 TOML 中的位置，确认会用后再改 XML 的尺寸。

当前盒子没有关节，因此固定在世界中。这样更适合先做“抓香蕉、放入盒子”的简化任务。若以后让盒子也能被推动，需增加自由关节与质量/惯量，并同步更新模型状态处理。

## 6. 预览时机械臂为什么不抓香蕉

预览只给 ALOHA 执行器持续设置初始关节目标，目的是检查场景。机械臂会受物理作用，并不保证每个关节完全静止。

当前云端的 `pi0_aloha_sim` 与传递方块任务配套。新加香蕉、盒子或改一句语言提示，都不能保证它学会这个新任务。现有 `run --config configs/aloha_sim.toml` 仍运行传方块；`scene` 入口不向远端发送动作请求。

本项目现已另外添加香蕉任务的 π0 控制入口、动作适配、稀疏奖励和成功终止逻辑。保持云端服务及端口转发，在 Mac 执行：

```bash
bash scripts/run_mac.sh run --config configs/banana_pi0.toml --display
```

具体步骤见 [香蕉夹取与 π0 运行](香蕉夹取与π0运行.md)。π0 入口尚未在本次执行，默认权重对新任务不保证成功。固定场景的脚本专家和演示采集已另行实现，见 [仿真专家演示采集](仿真专家演示采集.md)；遥操作与更广布局采集仍需后续准备。

后续完整路线是：

1. 在预览中确认物体不穿桌、盒子四壁有碰撞、香蕉能稳定落在桌面上。
2. 接入遥操作或单独的脚本专家，确认机械臂能抓取、抬高越过盒沿、放下并松爪。
3. 验证现有成功判定：曾夹起香蕉，之后完整入盒、脱离机械臂接触、有盒体支撑且稳定保持；仅中心点位于盒子上方不算成功。
4. 逐步随机化香蕉位置和朝向，采集成功演示。
5. 保存同步的相机 RGB、14 维机器人状态、14 维执行动作、语言指令、episode 和时间戳，再转换为原版 π0 的训练格式。
6. 在云端用匹配的数据适配、归一化统计和训练配置微调原版 π0，并接回新场景评估。

模型输入的机器人状态仍可保持 14 维：左臂 6 个关节和夹爪、右臂 6 个关节和夹爪。MuJoCo 内部有 16 个机械臂物理关节位置，再加香蕉的 7 维自由位姿；这些内部量不能直接当作原模型的 14 维输入。

盒子和香蕉的真实位姿可以用于记录与判定成功；是否把它们作为策略输入，必须与训练和部署时的输入设计一致。

## 7. 常见问题

### 窗口没有出现

先运行带 `--snapshot-only` 的命令，查看终端输出和 `scene.png`。如果仍报错，将完整报错贴出来。预览依赖 Mac 的本地图形环境；不要为这个本地入口设置 Linux 用的 `MUJOCO_GL=egl`。

### 香蕉掉到桌子下面或飞走

检查初始位置是否超出桌面、是否与桌面或机械臂严重重叠、XML 中的尺寸是否写错。先恢复默认摆放，再逐项调整；物理表现需要实际运行确认。

### 我想用鼠标拖着香蕉摆放

当前窗口展示的是相机画面，提供视角切换、暂停、重置和截图。摆放通过 TOML 修改。鼠标拖动物体需要另外接入交互式 MuJoCo 查看器或场景编辑器。

### 改场景要重新下载 π0 权重吗

只搭建和预览这个场景不需要模型权重。训练新任务则需要选择原版 π0 的初始化检查点，并准备数据和训练配置。
