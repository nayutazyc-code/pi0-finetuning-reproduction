# Original pi0 reproduction architecture

## Scope

The project is a Mac simulation and data-preparation client with Linux NVIDIA GPU model execution. It adapts original pi0 to an ALOHA-style transfer-cube baseline and a custom banana-in-box simulation. The local source includes supervised fine-tuning integration, not an autonomous reinforcement-learning loop or a physical-arm SDK integration.

The project's [pinned upstream source record](../sources.lock.json) identifies `repos/openpi/`. This is independent of the sibling workspace checkout. The Mac environment is project-local; training and serving use the Linux openpi environment. [pyproject.toml](../pyproject.toml) defines the Mac package boundary.

## Inference data flow

```text
Mac simulator -> image + joint state + instruction
                         |
Mac: metadata validation + observation adaptation
                         |
               WebSocket / SSH tunnel
                         |
Linux: source/model checks + preprocessing + pi0 inference
                         |
                    action chunk
                         |
Mac: action validation -> chunk scheduling -> target limits -> simulation
                         |
                recordings and next observation
```

The ALOHA interface supplies a top camera image, 14-dimensional joint/gripper state, and text prompt. The policy returns a sequence of absolute ALOHA joint/gripper targets. The current [banana baseline configuration](../configs/banana_finetuned_pi0.toml) retains synchronous inference, preserves the original image resolution, and executes a complete configured chunk before requesting another. The paired [training configuration](../configs/banana_finetune_roi.toml) selects shared ROI processing. Camera layout, normalization assets, action semantics, scene controller, and checkpoint must agree across data preparation, training, and serving.

The current user-selected [final operation profile](../configs/banana_final_pi0.toml) combines candidate999 weights, simulated wrist damping2, generation-time RTC20 and a separate 20-step quintic client bridge, with explicit checkpoint/normalization pins. The [final launcher](../scripts/run_final_pi0.py) owns policy selection, compatibility verification, its forwarding lifecycle and runtime receipts. Normal completion retains the selected service; errors after selection trigger an attempted verified v6 fallback. V6 remains the reference/fallback, while the historical v3 profile and generic ALOHA CLI default retain their own behavior. The user's 2026-10-30 selection is an operational preference, not a reversal of the [preceding acceptance result](final-candidate-acceptance-20261030.md). Commands and lifecycle limits belong in the [final runtime guide](final-runtime.md).

The optional [smooth-execution candidate](../configs/banana_smooth_pi0.toml) changes transport and execution without retraining the policy. It is a candidate for broader evaluation, not a replacement for the synchronous baseline. The [operational guide](smooth-execution.md) separates its prerequisites, commands, artifact interpretation, and rollback from this architecture.

The client validates declared model family, policy configuration, action dimension, and upstream commit before sending observations. It rejects invalid action shapes or non-finite values. The server checks the expected source revision and original `Pi0Config(pi05=False)`. Optional client settings can additionally require a relative checkpoint suffix and a 64-character lowercase normalization SHA-256 digest; mismatching server metadata is rejected before observations are sent. Omitted pins preserve legacy behavior. These are compatibility checks, not independent authentication of remote weights/assets or full validation of every training setting.

The [SSH tunnel helper](../scripts/ssh_tunnel.sh) forwards a local loopback port to the remote loopback listener. The service speaks WebSocket policy messages, not an HTML user interface. Availability requires a running remote process and active transport; source configuration alone does not establish either.

The optional scene parameter `right_wrist_angle_kp_scale` belongs to [scene generation](../src/pi0_repro/scene.py), defaults to 1, and permits nondefault finite positive scaling only for `position_pd`. It scales the right wrist-angle position actuator gain/bias without changing other gains, damping or contact parameters. This is a simulated-plant intervention, distinct from policy weights, timestamped references and command limits; an opt-in gain change requires separate closed-loop evaluation.

## Optional transport and execution

Raw MessagePack observations can go directly to the policy service. With PNG transport selected, the client encodes the original RGB image and sends it to a separate loopback sidecar. The sidecar restores the image, verifies its pixel digest, and forwards the ordinary observation to the unchanged policy service. Metadata advertises PNG support only on the sidecar connection; the client rejects a PNG configuration against a service without that capability. The currently supported compressed input is one `cam_high` image with 640 by 480 RGB pixels. State, prompt, policy actions, and server-side ROI preprocessing retain their original semantics. The digest checks pixel integrity, not endpoint identity or checkpoint authenticity. See the [transport decision](decisions/0001-lossless-image-transport.md) for alternatives and consequences.

The [executor](../src/pi0_repro/execution.py) supports at most one background inference request. Configuration may express the request age explicitly as `request_interval_steps`; the loader converts it to the complementary prefetch window and rejects conflicting explicit values. This nominal request age is distinct from prediction length and actual replacement time. An action's offset is measured from the simulation step at which its observation was captured. When a replacement arrives, the executor skips expired prefix actions, switches to the aligned suffix, and can blend arm-joint targets over a short transition. Fully stale chunks are discarded. A 50-step validity horizon therefore does not mean that all 50 actions from every accepted chunk are executed. Initial acquisition and an exhausted horizon can still block; wall-clock pacing is required for asynchronous mode but does not guarantee that network or inference deadlines are met.

The optional [RTC configuration](../configs/banana_rtc_pi0.toml) requires generation-time prefix guidance in addition to background scheduling. The executor forecasts the old valid plan through a copied target limiter and the environment's pure action projection, including physical finger-actuator bounds beyond nominal gripper limits, and sends native 14-dimensional absolute ALOHA targets with their valid overlap and estimated delay. The [server adapter](../server/rtc_policy.py) applies the ordinary serving transforms, including checkpoint normalization and model-dimension padding, and guides the clean-action estimate using a vector-Jacobian product during flow integration. Guidance weights include the 14 real joint/gripper dimensions and exclude padded dimensions. Metadata declares the explicit `pi0-rtc-v1` capability and the loaded adapter source digest; an RTC client rejects a service without the schema. Source-digest metadata is generated at service startup, not refreshed when a file changes. This path requires the pinned original-pi0 JAX banana policy and does not modify checkpoint parameters or upstream source.

A guided replacement arriving outside the old plan's valid overlap is discarded. The projected prefix consists of command targets, not a physical-state forecast; guidance is soft and does not guarantee exact continuity or deadlines. Startup uses zero temporal weights to compile the guided graph; later requests with no valid overlap reuse the same zero-weight path rather than first compiling a separate plain sampler during a stall. Extra differentiation can increase inference latency. Earlier RTC profiles can retain zero client-blend steps; the current final profile uses a 20-step quintic arm-reference crossfade in addition to its 20-step generation-time guidance taper. These are separate mechanisms. Actual execution and copied-limiter RTC forecasting share a pure timestamped reference, including unfinished earlier transitions, while grippers remain unblended. The client bridge length is bounded by old-plan validity and it never extends expired actions. Nonzero legacy linear blending is rejected with RTC; quintic weight smoothness does not guarantee physical or discrete-reference C2 continuity. See the [decision](decisions/0002-generation-time-action-prefix.md) for alternatives and the [operational guide](rtc-and-recovery.md) for deployment and comparison.

The optional [temporal-ensemble reference](../src/pi0_repro/execution.py) replaces client chunk crossfading with a bounded set of accepted valid plans. It averages arm-joint predictions for the same timestamp with normalized oldest-first age weights; grippers retain the newest valid raw targets. Execution and copied-limiter RTC forecasting share this pure reference, including future contributor expiry. Ensemble mode requires asynchronous requests and excludes nonzero chunk blending. This changes command-reference selection without changing the model or server; it does not predict physical joint states or guarantee continuity.

The target limiter preserves separate arm-joint and gripper velocity limits. Its optional acceleration limit applies to commanded arm-joint targets, not physical joint acceleration; grippers are excluded from acceleration limiting and chunk blending. Actuator bounds can override the target acceleration constraint at a stop. These controls can alter the policy's realized trajectory, so task success and smoothness both require evaluation. Optional critically damped arm-reference filtering precedes these bounds and excludes grippers. Constrained filter state is reanchored to executed command targets, and copied RTC forecasting retains the same filter state and actuator projection. Filtering can introduce lag and does not change the underlying position-controller gains or create task-phase/gripper decisions. The [Mac tuning guide](mac-motion-tuning.md) separates candidate comparisons from the selected baseline.

The optional [local jerk-reference backend](../src/pi0_repro/jerk_reference.py) follows the filtered arm target with numeric position/velocity/acceleration state and per-step stateless Ruckig calculations. It excludes grippers and retains independent input-filter state; copied RTC forecasting repeats the same calculation and projection. The legacy backend remains the default. Hard actuator projection resets affected reference derivatives and is outside the nominal kinematic guarantee, as is physical contact response. Optional dependency and evaluation details remain in [Mac tuning](mac-motion-tuning.md).

MuJoCo stepping and display event handling remain on the main thread. The optional banana-only render-on-request path returns current state without per-step pixels and supplies a fresh main-thread camera frame when inference, display, or video needs it. A same-control-step cache shares that frame; fresh inference never intentionally substitutes a previous step's image. Video sampling frequency is a configurable integer divisor of the fixed 50 Hz control rate and does not retime actions. The default display backend is Matplotlib; the smooth candidate selects a native GLFW viewer that uploads camera pixels to an OpenGL texture, restores the previous GL context after drawing, and leaves other simulator contexts alive. Closing the window or pressing Escape aborts the episode through the shared cleanup and recording path. Display updates normally follow a separately anchored clock. The optional before-step pacing mode attempts one draw per control step when the selected display rate is at least 50 Hz; neither schedule guarantees an achieved refresh rate. Optional video encoding uses a bounded worker queue, retains every submitted frame, and applies backpressure when the queue is full; it does not promise lossless video compression. The default `after_step` pacing waits after physics; opt-in `before_step` prepares observations, display work, and targets before waiting immediately ahead of action application. The opt-in mode shifts its next slot after an application miss above 2 ms to avoid compensating a late action with a short interval; the legacy mode retains its whole-period reset. Both avoid catch-up bursts through expired deadlines. This remains one main-thread loop, without a separate physics thread or interpolated display states. Native title updates are rate-limited independently of camera-frame draws. Application-start and completed-draw timestamps with local stage durations distinguish control and display cadence; deadline lateness identifies its application-start or loop-end measurement phase. See [Mac tuning](mac-motion-tuning.md) for configuration and diagnostic semantics. Rendering, encoding backpressure, and inference underruns can still delay the control loop.

Optional multi-view presentation leaves policy `cam_high` top RGB at 640×480 and its missing-wrist masks unchanged. Extra front/side world cameras and a right-gripper-mounted display camera feed only a spawned [read-only renderer](../src/pi0_repro/async_multiview.py). The control process submits small physics-state snapshots; the clone sets/forwards state without stepping physics, renders with display-only shadow reduction, and shares the latest composed RGB. Main-thread presentation polls that frame without waiting for a running render. Bounded startup/terminal frame waits occur outside running-control pacing. Source/target timestamps expose old or repeated display snapshots, which never replace fresh policy observations. Top video remains separate from optional composed video/frame-age logs. This additional rendering process does not create a physics/control thread or guarantee zero display delay, achieved frame rate, or fixed wall-clock control timing.

Policy-camera object reuse is separately opt-in in [the banana environment](../src/pi0_repro/banana_env.py): it preserves camera inputs and physics while returning independent RGB copies. Optional `display_in_worker` moves the GLFW window and drawing to the existing renderer subprocess's main thread; control sends snapshots and checks close/error signals rather than drawing. Close signals propagate through the normal partial-save/cleanup path. Legacy lifecycle and main-process presentation remain defaults. These resource-lifecycle choices do not add policy cameras, a physics thread, or a real-time guarantee; options and evidence are separated in [multi-view operation](random-pose-multiview.md).

## Demonstration and training flow

```text
Configured scene/layouts -> scripted expert -> candidate episodes
                                                |
                                      explicit review records
                                                |
                           accepted episodes -> LeRobot export
                                                |
                     Linux statistics + supervised fine-tuning
                                                |
                        checkpoint/assets -> serving -> evaluation
```

Layout membership and review decisions are data provenance. Accepted demonstrations supply supervised action targets. Simulator rewards and success markers support evaluation; their existence does not imply reward-driven policy updates. The training adapters use the original-pi0 flow-matching objective with task configuration, including optional weighting and projection training. Implementation and exact hyperparameters remain in source and TOML.

The project-local [training configuration adapter](../server/banana_config.py) can select the model's action horizon without changing upstream source. For optional single-GPU [gradient accumulation](../server/banana_accumulation.py), the loader supplies an effective batch equal to microbatch size times accumulation count; the adapter evaluates microbatches serially with unchanged weights, averages gradients, and invokes one optimizer update. Clipping and optional EMA follow that averaged update path. Training-state steps, learning-rate schedules, and checkpoint intervals count optimizer updates rather than microbatches. The [probe](../server/banana_probe.py) measures disposable real-data updates and GPU memory independently of a saved training run. Operational selection, resume, and long-horizon compatibility checks are in [long-chunk training](long-chunk-training.md); a configured horizon or budget does not establish a completed checkpoint or model improvement.

An optional [expert-displacement training objective](../server/banana_temporal.py) compares adjacent predicted clean arm-action displacements with expert displacements in native radians while retaining original flow matching. [Training-only data wrappers](../server/banana_temporal_data.py) supply explicit per-episode validity masks so terminal padding is excluded without treating static or zero actions as invalid. The matched control uses the same data/metric pipeline with zero auxiliary weight. Grippers, padded axes, and inference-time action selection are outside this auxiliary objective; no upstream observation or model-source edit is required. Operational details and experiment evidence belong in [long-chunk training](long-chunk-training.md) and the dated reports.

The expert has separate precision/transit Cartesian speed scales. Layout planning can vary table appearance and lighting in addition to object placement while assigning splits before collection. A structural audit blocks malformed/incomplete candidates; phase target-speed measurements are advisory and do not automatically approve or discard demonstrations. Explicit human or user-delegated assistant review remains required.

The recovery collector accepts only a preassigned training source episode and an original-pi0 learner recording from the same canonical scene. It replays executed controls, checks observed-state agreement at takeover, and saves the resulting full physical snapshot and source/checkpoint/hash provenance. Expert labels begin after takeover; learner actions establish the visited state but are not training targets. Supported states are table-resting or currently pinched bananas, not arbitrary failures. Physical state is preserved while segment-local counters/timestamps restart. Correction IDs retain parent lineage and do not count as independent layouts. An opt-in recovery-specific expert entry can skip the normal opening/hover from sufficiently close, aligned table-resting takeover states; it is enabled only with recovery metadata and an explicit expert setting. Physically held states retain closure before placement. This remains offline label generation and never supplies a runtime policy fallback; ordinary expert collection keeps its default entry behavior. An optional finite `recovery_grasp_min_height` in [expert configuration](../src/pi0_repro/banana_expert.py) adjusts only recovery-mode table-resting descend clearance; ordinary/default and already-held paths remain unchanged, and alternate labels require separate review. Separate mutually exclusive offline options can bridge the previous executed target toward moving expert targets or unload table-resting recovery arms toward their measured starting configuration before expert motion; previous learner commands establish a continuity boundary, not future training targets. These paths do not enter policy inference.

Reviewed batches can be copied into a new versioned aggregate without changing original files, split membership, or review lineage. The exporter revalidates acceptance and preserves split datasets. The [quality-training preparer](../scripts/prepare_quality_training.py) builds a train-only group/episode/phase sampler tied to the exported manifest digest and a conservative continuation configuration. The [motion-training preparer](../scripts/prepare_motion_training.py) instead binds an exported motion dataset to a parent-balanced group sampler that also reweights [expert event windows](../server/banana_event_sampling.py), and emits a versioned configuration; its pilot is prepared but not deployed. The [normalization adapter](../src/pi0_repro/normalization_assets.py) can create an explicitly versioned action-standard-deviation floor while retaining state statistics, action means, and quantiles. This changes action coordinates and is not an exactly function-preserving checkpoint initialization. Its asset report binds source/target hashes to the training dataset; adapted training, evaluation, and checkpoint-matched serving are required. Reusing previous statistics remains appropriate only after checking compatibility with new data, especially nearly constant axes exposed by correction trajectories. Preparing a configuration does not start training or establish a new checkpoint result. Operational sequencing and limits are in [RTC and recovery](rtc-and-recovery.md).

## Artifacts and limits

`data/` stores demonstrations and exported datasets; `outputs/` stores run artifacts. Neither is the maintained architecture specification. Recordings retain raw policy actions, blended targets, submitted and executed targets, prediction origins and per-action source offsets. New RTC recordings additionally save sent prefixes, request steps and valid lengths; latency logs retain prefix digests and the discrepancy between forecast and executed command targets during the inference interval. That discrepancy does not measure physical-state tracking error. Control and latency logs distinguish startup waits, horizon underruns, deadline lateness, and transport timing; this provenance is needed when interpreting asynchronous runs. Episode summaries identify the selected display backend and record native frame count and cumulative drawing time; those native counters do not measure Matplotlib frame rate. Video playback timing follows simulation time. Synchronous mode waits for inference; optional asynchronous prefetch can overlap inference with control, and wall-clock pacing records lateness rather than guaranteeing deadlines. Rendering, recording, network delay, and action-horizon underruns can still delay execution. A configured simulation frequency or pacing mode does not establish an achieved wall-clock control rate. New recordings include inclusive stage timings, geometry-based near-grasp progress, meaningful gripper-command reversals, and target changes at chunk switches. Stage timers can overlap and are not an exclusive CPU-time decomposition. Near-grasp geometry is diagnostic only, never a policy input or a relaxed success condition; older logs lacking that field report unavailable proximity times. Frozen-action replay is open-loop diagnosis and cannot establish a closed-loop policy improvement. Repeated layout evaluation preserves layout seeds but does not pair stochastic policy samples.

The Mac `run` workflow supports transfer-cube and the custom banana environment. LIBERO uses an observation-file interface locally; full matching simulation requires its own environment. No remote process or success rate is asserted here. Existing results are scoped in the [documentation index](README.md), and [server instructions](../server/README.md) describe deployment rather than proving current availability.

The [PNG sidecar](../server/image_transport_proxy.py) exposes versioned transport envelopes separately from model inference timing. Its nested unpack/decode/upstream-round-trip/handler spans are not an additive CPU decomposition, and the upstream previous-loop total includes receive waiting. A bounded `/transport-probe` WebSocket echo bypasses the model connection and policy state entirely; it is a diagnostic interface, not a second inference API. Pixel digest validation and the observation/action protocol remain the inference-path boundary.

The [progress-continuation supervisor](../server/progress_train_job.py) binds train-only repositories, source/configuration hashes, normalization and storage checks before reader/probe/training stages. Held-out lineage is compared locally; cloud validation consumes a digest/count attestation rather than held-out contents, which is not independent remote inspection or enforced filesystem isolation. The separate [progress policy selector](../server/progress_policy_select.py) checks registered committed checkpoints and process ownership before dispatch; availability still requires metadata verification. Training and inference selection remain separate from offline recovery-label generation.

Optional [deferred top-video capture](../src/pi0_repro/deferred_video.py) separates running observation production from recording presentation. Live policy images remain fresh in the control process; a bounded matrix captures integration snapshots at video-sample steps, and a clone restores/forwards them for top-camera rendering/encoding only after control and worker cleanup. It never steps the clone or substitutes replayed pixels for observations. This BananaBox/render-on-request recording option defaults off, permits display only through the existing worker path, and persists captured states before encoding so failures retain diagnostic evidence. Capture and post-control costs remain distinct; it changes neither model/RTC semantics nor a wall-clock deadline guarantee.


The pure [application-deadline helper](../src/pi0_repro/pacing.py) owns before-step deadline arithmetic separately from physics and target generation. Default behavior remains unchanged; optional post-apply overrun recovery removes an additional finish-based idle interval without changing the normal anchored clock or guaranteeing actual application intervals. Optional BananaBox timing traces expose environment subphase wall/thread/process spans and sleep/deadline/GC provenance; diagnostic collection is separate from control decisions and removes hooks on cleanup. Operation and experimental limits are documented in [Mac motion tuning](mac-motion-tuning.md#optional-post-apply-overrun-recovery-and-timing-traces).

The optional offline expert `continuous_transport_radius` leaves the zero/default, already-held and direct-release paths unchanged. After closure in ordinary/table-resting recovery, [expert path generation](../src/pi0_repro/expert_path.py) can combine virtual-distance C2 corner rounding with smooth velocity ramps before IK. Cartesian profile bounds do not guarantee physical servo/contact derivatives; these teacher paths remain outside runtime policy execution and require separate data review and model evaluation.
